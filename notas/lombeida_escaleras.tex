\section*{LOMBEIDA ESCALERAS — Tolerancia a fallos y conclusiones}

\noindent\textit{Tiempo previsto: 3 minutos, aproximadamente uno por diapositiva.}

\paragraph{10. Tolerancia a fallos.}
El sistema debe seguir prestando servicio pese a fallos de nodos, comunicación, procesos o recursos. Un fallo puede producir un error interno y, si llega al usuario, una falla del servicio. En un cálculo paralelo, perder el resultado de un trabajador puede impedir completar el conjunto.~\cite{assiri2025,mushtaq2024}

\paragraph{11. Detección y recuperación.}
Un \emph{heartbeat} indica actividad, no necesariamente avance; un \emph{timeout} hace sospechar un fallo, pero también puede deberse a una demora. Un \emph{watchdog} vigila señales esperadas.~\cite{chaurasia2024,asch2025}
Para recuperar el trabajo se puede usar una réplica, reasignar la tarea o reanudar desde un \emph{checkpoint}. Reanudar desde un estado guardado no es lo mismo que reintentar una tarea.~\cite{mushtaq2024}

\paragraph{12. Aplicación a SGRA.}
El estudiante solicita un refuerzo y el docente lo programa. Un programa Java externo comprobó cuatro franjas con uno y con cuatro trabajadores: los resultados coincidieron y las tareas se solaparon. Ante un fallo simulado, solo se reintentó la comprobación afectada. Si vuelve a fallar, la franja queda sin comprobar, no libre. La lección para el PFC es recuperar solo el trabajo perdido: el reintento no se aplica a la aceptación en SGRA. La práctica no prueba un incidente real ni paralelismo dentro del backend.
