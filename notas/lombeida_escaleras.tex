\subsection*{Diapositiva 10 — Tolerancia a fallos y tipos de fallos}

\textbf{Idea central.} La tolerancia a fallos es la capacidad de un sistema distribuido de seguir funcionando correctamente cuando se producen fallos.~\cite{assiri2025} En un sistema distribuido no se puede evitar que algo falle; lo que sí se puede hacer es evitar que ese fallo se convierta en una interrupción del servicio.

\textbf{Relación con la computación paralela.} Cuando una ejecución paralela se reparte entre varios nodos, cada trabajador procesa una parte del trabajo al mismo tiempo que los demás. Si uno falla, las tareas que dependen de su resultado pueden quedar esperando y el resultado conjunto puede no completarse. La tolerancia a fallos busca recuperar esa parte del trabajo sin perder innecesariamente lo que ya terminaron los otros trabajadores. Por ejemplo, si cuatro trabajadores procesan cuatro bloques de datos y uno cae, los otros tres resultados no bastan si el cálculo necesita los cuatro bloques. Este es un ejemplo didáctico, no una descripción de una ejecución comprobada en SGRA.

\textbf{Fallo, error y falla.} Conviene distinguir tres términos que suelen confundirse. El \emph{fallo} es la causa o defecto interno; el \emph{error} es el estado incorrecto que ese defecto produce; y la \emph{falla} es la pérdida del servicio que percibe el usuario.~\cite{mushtaq2024} La cadena es fallo $\rightarrow$ error $\rightarrow$ falla, y la tolerancia a fallos busca cortarla antes de que llegue al usuario.

\textbf{Tipos de fallos.} Se agrupan en cuatro tipos~\cite{mushtaq2024}:
\begin{itemize}
  \item \textbf{Nodos:} una máquina se cae o responde muy lento.
  \item \textbf{Comunicación:} los mensajes se pierden, se duplican o llegan tarde.
  \item \textbf{Procesos:} un proceso se bloquea o entrega una respuesta incorrecta.
  \item \textbf{Recursos:} se agota la CPU, la memoria, el disco o la red.
\end{itemize}

\textbf{Enlace con la siguiente diapositiva.} Ante estos fallos, necesitamos saber qué trabajador dejó de responder y cómo recuperar sus tareas. Después trasladaremos las lecciones de continuidad al escenario de SGRA en el que Groq Cloud no responde a tiempo.

\subsection*{Diapositiva 11 — Detección y recuperación ante fallos}

\textbf{Guion sugerido (aproximadamente 1 minuto).}
En computación paralela distribuida, varios trabajadores ejecutan partes del mismo trabajo simultáneamente. Si uno falla, puede impedir completar el resultado conjunto.
Los \emph{heartbeats} indican que los trabajadores siguen activos; un \emph{timeout} permite sospechar un fallo si dejan de responder. Una demora de red también puede dispararlo: no demuestra que el nodo haya caído.~\cite{chaurasia2024}
Los \emph{watchdogs} vigilan señales esperadas dentro de un plazo; pueden servir para supervisar la ejecución si esas señales se vinculan a su avance.~\cite{asch2025}

Para recuperar el trabajo paralelo, la replicación aporta copias, la reasignación pasa tareas pendientes a otro trabajador y el \emph{checkpoint} permite retomar un estado guardado, evitando repetir todo el cálculo.~\cite{mushtaq2024}
Así buscamos completar el trabajo pese al fallo de una parte. En SGRA aplicaremos la lección de continuidad al respaldo Java, sin confundir ese respaldo con ejecución paralela.

\textbf{Apoyo para preguntas.}
Un heartbeat confirma actividad, pero no necesariamente avance útil: un proceso puede seguir enviándolo aunque una tarea esté bloqueada. Para vigilar progreso deben definirse señales o métricas relacionadas con el trabajo realizado.
En el ejemplo de los cuatro bloques, reasignar el bloque pendiente a otro trabajador permite intentar completar el resultado conjunto. Si el trabajo tiene efectos externos, también debe controlarse la ejecución duplicada.
Un checkpoint debe guardar el estado necesario para reanudar; cuando hay dependencias entre trabajadores, puede requerirse coordinar los estados recuperados.
Un timeout demasiado corto puede generar falsas sospechas; uno demasiado largo demora la reacción.
La redundancia es disponer de elementos adicionales, mientras que la replicación es una forma de redundancia basada en copias.
Reiniciar desde un checkpoint no significa lo mismo que reintentar una petición: aquí se explica recuperación de estado, no una política de reintentos con backoff.
El respaldo local de SGRA se describe en el documento interno \textit{SGRA: descripción técnica y funcional}; no se atribuye a las fuentes bibliográficas ni se presupone que tenga las mismas capacidades que Groq.
Groq $\rightarrow$ validador Java es una alternativa activada ante un fallo, no evidencia por sí sola de computación paralela. Las diapositivas 10 y 11 explican los mecanismos generales y su aplicación al trabajo paralelo; SGRA ilustra cómo trasladar la lección de continuidad a la PFC.

\subsection*{Diapositiva 12 — SGRA: lecciones para la PFC y conclusiones}

\textbf{Guion sugerido (aproximadamente 1 minuto).}
En nuestra PFC, SGRA, el documento técnico describe un respaldo: si Groq Cloud falla o no responde, interviene un validador Java local.
Lo presentamos como un escenario previsto, no como un incidente ya comprobado.
La falta de respuesta es un síntoma; sin registros ni pruebas no podemos confirmar la causa raíz.

Las lecciones que proponemos aplicar son definir límites de espera, probar que se activa el respaldo y registrar errores y tiempos para investigar el problema.
El validador no sustituye todas las capacidades de la IA: conserva una función de validación, no demuestra paralelismo.

La conclusión para la computación paralela distribuida es que repartir el trabajo no basta: también hay que recuperar las tareas de los trabajadores que fallan para completar el resultado conjunto.~\cite{assiri2025,mushtaq2024}
SGRA permite trasladar esa lección de continuidad a nuestra PFC, aunque su respaldo sea un mecanismo distinto.

\textbf{Fuente del escenario.}
El documento interno \textit{SGRA: descripción técnica y funcional}, sección 4, apartado «Integraciones externas», describe Groq Cloud y el validador Java de respaldo.
Se menciona como contexto del proyecto y no se incorpora a la bibliografía académica.
No hemos realizado todavía la prueba controlada ni verificado código o registros que demuestren la activación del respaldo.

\textbf{Apoyo para preguntas: síntoma, causa y recuperación.}
Una ausencia de respuesta puede deberse a problemas de comunicación, indisponibilidad del proveedor u otras condiciones; son hipótesis, no causas confirmadas.
La dependencia de un servicio externo es una condición arquitectónica de riesgo, no la causa raíz demostrada de un incidente.
Para distinguir las hipótesis se necesitarían registros del error, tiempos de la solicitud y evidencia del comportamiento del proveedor y del backend.
El paso al validador Java es una alternativa funcional de respaldo, no una réplica de Groq ni una ejecución simultánea de ambos.

\textbf{Alcance de las lecciones propuestas.}
Definir límites de espera, probar la activación del respaldo y registrar su uso son recomendaciones para la PFC, no funcionalidades cuya implementación hayamos comprobado.
La prueba práctica y sus evidencias se prepararán después; no se atribuyen resultados ni tiempos de recuperación todavía.
El ejemplo de trabajadores paralelos de las notas anteriores es didáctico y no implica que SGRA ejecute ese flujo.
